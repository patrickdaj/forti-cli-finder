# Multi-build bundles (FortiOS 8.0 alongside 7.6.7) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let one build of the site carry more than one firmware build per platform, and add the 8.0 CLI References alongside 7.6.7 so `/ver` actually has something to pick between.

**Architecture:** Today `sources.json`'s `product` field is overloaded: it is both the platform identity (FortiGate vs FortiSwitch) and the bundle filename (`site/data/fortios.json`). Two builds of FortiOS therefore collide. This plan splits those two meanings apart — a new `bundle` key names the file, `product` keeps naming the platform — then adds the 8.0 entries. The page already supports multiple builds (`site/index.html:214`: *"To add a build: put its bundle in data/ and add {v,f,src} to that platform's vers"*); what it does not have is a build pipeline that can produce them, so the `PRODUCTS` literal becomes generated by `stamp_build.py` the same way `BUILD` already is.

**Tech Stack:** python3 stdlib only, `pdftotext` (poppler), vanilla JS in one HTML file. No new dependencies — this is a hard constraint of the project.

**Spec:** `/private/tmp/claude-501/-Users-patrick-Development-forti-cli-helper/370df20f-e808-4fc3-bc33-cc7be114e854/scratchpad/research-2-getshow-tree.md` §"Incidental finding worth acting on separately" (the 8.0 delta measurement), plus the conversation decision that multi-build support "must" exist.

## Global Constraints

- **No new runtime or build dependencies.** python3 stdlib plus `pdftotext` only. The bundles ship to a browser from a static host; there is no server.
- **`sources.lock.json` stays committed and authoritative.** Every PDF a build reads is pinned there by URL, filename and byte size. Never fetch an unpinned document during a build.
- **Backward compatibility of `sources.json`:** a `cli` entry without a `bundle` key must keep behaving exactly as today (`bundle` defaults to `product`). The four existing entries are not to be rewritten in Task 1.
- **Bundle key names stay single-letter** where they ship per-section (`k`, `p`, `d`, `pg`, `s`, `x`, …). Bundle-level metadata keys may be longer.
- **Bundle filenames** are `<bundle>.json` in `site/data/`, where `<bundle>` matches `^[a-z0-9]+(-[0-9.]+)?$`. The current four keep their exact present names (`fortios.json`, `fortiswitch.json`, `fortianalyzer.json`, `fortimanager.json`) so existing links and caches are undisturbed.
- **`/ver` labels** come from the `ver` and `src` fields in `sources.json`, never hand-typed into `index.html`.

## Review Focus

Five conditions the spec implies but no task's happy path exercises. Each has a test assigned to the task that owns the code.

1. **A `cli` entry with no `bundle` key** must still build to `<product>.json`. The whole backward-compatibility claim rests on this and it is one `.get()` away from breaking. → Task 1, Step 1.
2. **Two bundles with the same `product`** must not overwrite each other, and `attach_outputs.py`'s `B = {p: ...}` dict is keyed by exactly the thing that is now duplicated. → Task 2, Step 1.
3. **A sample whose `target` names a bundle that does not exist** (a typo, or a guide left pointing at a removed build) must fail loudly at build time, not silently drop every sample from that guide. The current code would `KeyError` — which is loud, but the message names a product, not the source that caused it. → Task 2, Step 5.
4. **`derive_getshow.py` run twice** over a bundle that already has derived entries must not double them. It guards on `(kind, path) in have`, but `have` is computed once before the loop while `add` grows — worth pinning before the file is touched for multi-bundle. → Task 2, Step 6.
5. **A build where one platform has two versions and another has one** must produce a `/ver` listing that marks the right default per platform, and `P.vers[0]` is the implicit default. Order in `sources.json` therefore becomes load-bearing and nothing currently says so. → Task 4, Steps 2 and 6.

```python
#!/usr/bin/env python3
"""Check the built bundles hold together. Run by build.sh; also runnable alone.

Exits non-zero on the first failure with a message naming the bundle and what broke.
"""
import json, os, re, sys

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
OUT = os.environ.get('OUT', 'site/data')
NAME = re.compile(r'^[a-z0-9]+(-[0-9.]+)?$')


def bundle_id(entry):
    """The bundle a cli entry builds into. Defaults to the platform id, so an entry
    written before multi-build support keeps its present filename."""
    return entry.get('bundle') or entry['product']


def main():
    cfg = json.load(open(os.path.join(ROOT, 'sources.json')))
    fail = []

    ids = [bundle_id(e) for e in cfg['cli']]
    for b in ids:
        if not NAME.match(b):
            fail.append(f'bundle id {b!r} is not [a-z0-9]+(-[0-9.]+)?')
    if len(set(ids)) != len(ids):
        dupes = sorted({b for b in ids if ids.count(b) > 1})
        fail.append(f'two cli entries build into the same bundle: {dupes}')

    for e in cfg['cli']:
        b = bundle_id(e)
        path = f'{OUT}/{b}.json'
        if not os.path.exists(path):
            fail.append(f'{b}: {path} was not built')
            continue
        d = json.load(open(path))
        if d.get('id') != e['product']:
            fail.append(f"{b}: bundle id is {d.get('id')!r}, expected {e['product']!r}")
        if not d.get('secs'):
            fail.append(f'{b}: no sections')

    for f in fail:
        print(f'  FAIL {f}', file=sys.stderr)
    print(f'{len(ids)} bundles checked, {len(fail)} problems')
    return 1 if fail else 0


if __name__ == '__main__':
    sys.exit(main())
```

**The important part.** `tools/attach_outputs.py:110-120` currently resolves a multi-bundle
match by sorting and taking `hits[0]` — exactly one bundle gets the sample:


That tie-break exists to answer a **platform** question — does `show switch-controller …`
belong to FortiGate or FortiSwitch? — and taking one winner is right for that. It is wrong
once a platform has two builds: `fortios` and `fortios-8.0` would both match, one would win,
and the other would ship with almost no sample output. The rule has to become *disambiguate
across platforms, then attach to every bundle of the winning platform.* Replace the block
with exactly this:

```python
        if hits:
            if len({PLATFORM[h[0]] for h in hits}) > 1:
                # A guide that covers both ends of a FortiLink pair: decide by where the
                # command actually runs. This picks a platform, not a build.
                on_fgt = 'switch-controller' in cmd or (
                    'FortiGate' in smp['cap'] and 'FortiSwitch' not in smp['cap'])
                want = 'fortios' if on_fgt else 'fortiswitch'
                if any(PLATFORM[h[0]] == want for h in hits):
                    hits = [h for h in hits if PLATFORM[h[0]] == want]
            # Within one platform every build whose match is as long as the best one gets
            # the sample: a 7.6.7 guide is evidence about an 8.0 command too, and the
            # bundle records which guide it came from, so the page still labels it
            # honestly. A shorter match means a different, less specific command.
            best = max(h[1][1][0] for h in hits)
            for bundle, (i, score) in hits:
                if score[0] == best:
                    att[bundle][i].append(o)
                    stats[key]['attached:' + bundle] += 1
            continue
```

and `hits` is built at line 109 as `[(bundle, m) …]`. So `score[0]` is the matched path
length, which is what `best` compares.

```python
import json, os

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))

# One PRODUCTS entry per platform, with one `vers` entry per build, in sources.json order.
plats = {}
for e in CFG['cli']:

                                        'name': '', 'vers': []})
    p['name'] = (e.get('label') or '').rsplit(' ', 1)[0] or e['product']
    p['vers'].append({'v': e.get('ver', ''),
                      'f': e.get('bundle') or e['product'],
                      'src': e.get('src', e['title'])})

lines = []
for p in plats.values():
    vers = ','.join('{v:%s,f:%s,src:%s}' % (json.dumps(x['v']), json.dumps(x['f']),
                                            json.dumps(x['src'])) for x in p['vers'])

products = 'const PRODUCTS=[\n' + ',\n'.join(lines) + '];'
```
